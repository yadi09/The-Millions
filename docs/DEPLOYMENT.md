# Deployment runbook

This document covers two environments using the **same** scripts and the **same** Docker Compose stack:

- **EC2 dry-run** — AWS EC2 (Ubuntu 22.04, t3.small), used to validate the deployment process end-to-end before production. No real domain. Self-signed TLS.
- **Fast Host VPS production** — the real home. Real domain, Let's Encrypt TLS.

The only operational differences between the two are: the value of `SERVER_NAME` in `deploy/.env`, and whether `issue-cert.sh` produces a self-signed cert or a Let's Encrypt cert (it picks automatically based on `SERVER_NAME`).

---

## Architecture (single host)

```
                ┌─────────────────── host ───────────────────┐
                │                                            │
  internet ───▶ │  nginx :443/:80                            │
                │   ├─ /api/* ──▶ backend container :4000   │
                │   └─ /*     ──▶ static dist/ baked in     │
                │                                            │
                │  backend ──▶ postgres container :5432     │
                │              └─ named volume (data)       │
                │                                            │
                │  Daily: pg-backup.sh → /var/backups       │
                └────────────────────────────────────────────┘
```

- Only ports 80, 443, 22 are open at the firewall level.
- Postgres has **no published port** — it's reachable only on the internal Docker network.
- Backend has **no published port** — only nginx talks to it.
- All secrets generated by `init-secrets.sh`. Nothing committed.

## Part 1 — EC2 dry-run

### Prerequisites

- EC2 instance: Ubuntu 22.04 LTS or 24.04 LTS, t3.small (2 GB RAM), **20+ GB disk** (the default 8 GB AMI fills up during Docker install — expand the EBS volume to 20 GB before bootstrapping, then `sudo growpart /dev/nvme0n1 1 && sudo resize2fs /dev/nvme0n1p1`)
- Security group allows inbound: 22 (your IP), 80, 443 (0.0.0.0/0)
- SSH key working: `ssh -i your-key.pem ubuntu@EC2_PUBLIC_IP`

### One-time setup (per host)

```bash
ssh -i your-key.pem ubuntu@EC2_PUBLIC_IP

# 1) Clone the repo
git clone https://github.com/yadi09/The-Millions.git
cd The-Millions

# 2) Bootstrap the host (installs Docker, configures swap + ufw + backup dir)
./deploy/setup-server.sh

# 3) Log out and back in so the `docker` group takes effect on your shell
exit
ssh -i your-key.pem ubuntu@EC2_PUBLIC_IP
cd The-Millions
groups | grep docker   # should list `docker`

# 4) Generate secrets, then edit deploy/.env to fill in the rest
./deploy/init-secrets.sh
nano deploy/.env
#   SERVER_NAME=_                  (dry-run: match any host)
#   CORS_ORIGINS=https://EC2_PUBLIC_IP   (where EC2_PUBLIC_IP is your IP)
#   CLOUDINARY_*                   (from your Cloudinary dashboard — required)
#   ADMIN_EMAIL=admin@themillions.co.uk

# 5) Issue a self-signed cert (auto-detected because SERVER_NAME=_)
./deploy/issue-cert.sh

# 6) Deploy
./deploy/deploy.sh

# 7) Seed the database (first time only)
./deploy/seed-db.sh
```

### Verify

```bash
# Health endpoint (use -k because the cert is self-signed)
curl -k https://EC2_PUBLIC_IP/api/health

# Login
curl -k -X POST https://EC2_PUBLIC_IP/api/auth/login \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"$(grep ^ADMIN_EMAIL deploy/.env | cut -d= -f2)\",\"password\":\"$(grep ^ADMIN_PASSWORD deploy/.env | cut -d= -f2)\"}"

# Visit the site in a browser
open https://EC2_PUBLIC_IP   # click through the cert warning
```

### Common dry-run gotchas

| Symptom | Likely cause | Fix |
|---|---|---|
| `fallocate failed: No space left on device` during `setup-server.sh` | Root volume too small (default Ubuntu AMI = 8 GB; Docker fills it) | Expand EBS to 20 GB in AWS console, then `sudo growpart /dev/nvme0n1 1 && sudo resize2fs /dev/nvme0n1p1`. The patched `setup-server.sh` auto-removes stale `/swapfile` and tries smaller sizes (2G → 1G → 512M → skip) |
| Browser says "connection refused" | Security group not open on 443 | AWS console → security group → inbound rules → add HTTP/HTTPS from `0.0.0.0/0` |
| `docker: permission denied` | User not in docker group yet | log out + back in after `setup-server.sh` |
| Backend logs show "JWT_SECRET must be at least 32 characters" | `deploy/.env` wasn't sourced | the env file is loaded by compose's `--env-file`; verify path |
| CORS errors in browser console | `CORS_ORIGINS` doesn't include the URL you opened | add `https://EC2_PUBLIC_IP` to `CORS_ORIGINS` and redeploy |
| Postgres unhealthy after compose up | First boot can take 10–20s | wait; `docker compose logs postgres` shows progress |
| `type "public.ContactStatus" does not exist` during seed | Pre-existing migration drift — `schema.prisma` declares the enum but no migration creates it; `status` ends up as `text` in the DB | Run this once: `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env exec -T postgres psql -U "$POSTGRES_USER" "$POSTGRES_DB" -c "CREATE TYPE \"ContactStatus\" AS ENUM ('NEW','READ','REPLIED'); ALTER TABLE \"ContactMessage\" ALTER COLUMN status DROP DEFAULT; ALTER TABLE \"ContactMessage\" ALTER COLUMN status TYPE \"ContactStatus\" USING status::\"ContactStatus\"; ALTER TABLE \"ContactMessage\" ALTER COLUMN status SET DEFAULT 'NEW';"`. A proper Prisma migration for this is a follow-up backend fix. |

## Part 2 — Fast Host VPS production

### Prerequisites

- VPS provisioned with Ubuntu 22.04 (or 24.04 — same scripts).
- Domain purchased in Fast Host. **DNS A record** for `themillions.co.uk` (and `www`) pointing at the VPS public IP. Propagation can take up to an hour.
- Verify DNS before you start: `dig +short themillions.co.uk` should return the VPS IP.

### Steps (identical to EC2 except SERVER_NAME and cert source)

```bash
ssh you@VPS_PUBLIC_IP

git clone https://github.com/yadi09/The-Millions.git
cd The-Millions
./deploy/setup-server.sh
exit
ssh you@VPS_PUBLIC_IP
cd The-Millions

./deploy/init-secrets.sh
nano deploy/.env
#   SERVER_NAME=themillions.co.uk          (the real domain)
#   CORS_ORIGINS=https://themillions.co.uk,https://www.themillions.co.uk
#   CERTBOT_EMAIL=youraddress@example.com  (for Let's Encrypt notices)
#   CLOUDINARY_*
#   ADMIN_EMAIL=…

./deploy/issue-cert.sh   # detects real SERVER_NAME → runs certbot
./deploy/deploy.sh
./deploy/seed-db.sh
```

### TLS cert renewals

Let's Encrypt certs expire in 90 days. Renew via cron:

```bash
sudo crontab -e
# Add:
0 4 * * 1 /home/$USER/The-Millions/deploy/issue-cert.sh >> /var/log/themillions-cert.log 2>&1
```

`issue-cert.sh` short-circuits if the cert has >30 days left, so it's safe to run weekly.

### Daily Postgres backups

```bash
sudo crontab -e
# Add:
0 3 * * * /home/$USER/The-Millions/deploy/pg-backup.sh >> /var/log/themillions-backup.log 2>&1
```

Backups land in `/var/backups/themillions/YYYY-MM-DD.sql.gz`, 14-day retention.

For off-host storage, add an `aws s3 cp` or `rsync` step to `pg-backup.sh` — left out by default to keep the script provider-neutral.

## Day-2 operations

### Deploy a new version

```bash
ssh you@host
cd The-Millions
./deploy/deploy.sh
```

`deploy.sh` does: `git pull` → pre-deploy DB backup → `docker compose build` → `up -d` → wait for healthy → done.

### See logs

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs -f backend
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs -f nginx
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs -f postgres
```

Shorter form (alias in your shell):

```bash
alias dc='docker compose -f ~/The-Millions/deploy/docker-compose.prod.yml --env-file ~/The-Millions/deploy/.env'
dc logs -f backend
```

### Open a psql shell

```bash
dc exec postgres psql -U "$POSTGRES_USER" "$POSTGRES_DB"
```

### Rotate JWT secret (logs out all sessions)

```bash
# Edit deploy/.env, change JWT_SECRET to a fresh `openssl rand -hex 32`
nano deploy/.env
dc up -d --no-deps backend
```

### Rotate Postgres password

```bash
NEW_PW=$(tr -dc 'A-Za-z0-9' </dev/urandom | head -c 24)
dc exec postgres psql -U "$POSTGRES_USER" -d postgres \
  -c "ALTER USER \"$POSTGRES_USER\" PASSWORD '$NEW_PW';"
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=$NEW_PW|" deploy/.env
dc up -d --no-deps backend
```

### Restore a backup

```bash
./deploy/restore-backup.sh /var/backups/themillions/2026-05-15.sql.gz
```

Destructive — prompts for "RESTORE" confirmation.

### Stop everything

```bash
dc down       # stop containers, KEEP the data volume
dc down -v    # stop AND DELETE the postgres-data volume — destroys all DB data
```

## Migrating EC2 → Fast Host (when the dry-run is done)

```bash
# On the EC2 dry-run host: take a final backup
./deploy/pg-backup.sh
scp /var/backups/themillions/$(date +%Y-%m-%d).sql.gz \
    you@vps_public_ip:~/

# On the Fast Host VPS: follow Part 2 setup through `./deploy/issue-cert.sh`,
# then BEFORE `deploy.sh`:
mv ~/$(date +%Y-%m-%d).sql.gz /var/backups/themillions/
./deploy/deploy.sh
./deploy/restore-backup.sh /var/backups/themillions/<filename>.sql.gz
```

Skip `seed-db.sh` on the VPS — the data comes from the EC2 backup.

## What this setup intentionally does NOT do (yet)

- **Zero-downtime deploys.** Compose recreates the backend container in place; expect a ~5 s blip on each deploy. For true zero-downtime, add a second backend container behind nginx's `upstream` block.
- **Horizontal scaling.** Single host, single backend container. To scale: extract Postgres to RDS/managed, run multiple backend containers, put nginx behind a load balancer (ALB / Cloudflare).
- **Off-host backup storage.** Backups live on the same disk as the DB. Add `aws s3 sync` to `pg-backup.sh`, or rsync to another VPS, for real disaster recovery.
- **Application metrics / log aggregation.** Logs go to `docker logs` (rotated by Docker's default json-file driver). For production, point Docker at a log driver (e.g. CloudWatch, Loki) or run a Prometheus scrape against the backend.
- **Secrets management.** `deploy/.env` is the source of truth on the host. For multiple hosts or compliance, switch to AWS SSM Parameter Store / Hashicorp Vault.

These are deliberate omissions to keep the surface small. Add them when traffic or compliance demands them.
